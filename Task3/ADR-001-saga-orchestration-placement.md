## Контекст

OrchestrPay реализует платёжный процесс через Saga-оркестрацию. В рамках одного платежа система должна:

- создать платёжную операцию;
- списать деньги со счёта клиента;
- выполнить антифрод- и внешние проверки;
- обработать один из результатов проверки: разрешение, отказ или ручная проверка;
- ожидать решение оператора при ручной проверке;
- применять cut-off-time, если проверка не вернула результат вовремя;
- перевести деньги контрагенту при успешном сценарии;
- автоматически вернуть деньги клиенту при отказе или сбое;
- уведомить клиента и систему безопасности.

Ключевая архитектурная проблема: нужно определить, где должна жить логика управления Saga — внутри одного из доменных сервисов, например `Payment Service`, или в отдельном сервисе-оркестраторе.

Решение важно, потому что процесс затрагивает несколько сервисов и включает состояние, таймеры, ожидание ручной проверки, компенсационные транзакции, retry-механизмы, идемпотентность, мониторинг и восстановление после ошибок.

## Рассмотренные варианты

### Вариант №1 «Оркестрация внутри Payment Service»

В этом варианте `Payment Service` отвечает не только за доменную логику платежа, но и за управление всем процессом Saga.

`Payment Service`:

- создаёт платёж;
- списывает деньги;
- вызывает `FraudCheck Service`;
- ожидает результат ручной проверки;
- применяет cut-off-time;
- запускает перевод контрагенту;
- инициирует возврат;
- вызывает `Notification Service`;
- фиксирует состояния Saga.

Упрощённая схема:

```text
Client / Marketplace
        |
        v
Payment Service
  |     |      |
  |     |      +--> Notification Service
  |     |
  |     +--------> FraudCheck Service
  |
  +--------------> External Risk / Compliance Checks
  |
  +--------------> Bank / Payment Gateway
```
### Вариант №2 «Отдельный Saga Orchestrator Service»

В этом варианте функция Saga-оркестрации выносится в отдельный сервис - `Payment Saga Orchestrator`.

`Payment Saga Orchestrator` не выполняет доменные операции сам, а управляет порядком шагов платёжного процесса. Он вызывает нужные сервисы, фиксирует состояние Saga, обрабатывает развилки, запускает компенсации и контролирует таймеры.

Оркестратор отвечает за:

- запуск экземпляра Saga при создании платежа;
- управление переходами state machine;
- вызов `Payment Service` для списания, возврата и перевода денег;
- вызов `FraudCheck Service` для антифрод-проверки;
- обработку результатов антифрода: `ALLOW`, `DENY`, `MANUAL_REVIEW`;
- перевод платежа в ожидание ручной проверки;
- контроль таймера ручной проверки до 20 минут;
- применение cut-off-time, если проверка не вернула ответ вовремя;
- запуск компенсационной операции возврата клиенту;
- вызов `Notification Service` для уведомления клиента;
- отправку уведомления в систему безопасности при подозрительной операции;
- хранение и восстановление состояния Saga после ошибок.

Доменные сервисы при этом остаются сфокусированы на своих зонах ответственности:

- `Payment Service` выполняет операции со средствами: списание, перевод контрагенту, возврат клиенту;
- `FraudCheck Service` анализирует транзакцию и возвращает решение;
- `Notification Service` отправляет уведомления клиентам;
- `Payment Saga Orchestrator` управляет процессом, состояниями, таймерами и компенсациями.

Упрощённая схема взаимодействия:

```text
Client / Marketplace
        |
        v
Payment Saga Orchestrator
        |
        |--> Payment Service
        |       |
        |       |--> Debit customer account
        |       |--> Transfer to counterparty
        |       |--> Refund customer account
        |
        |--> FraudCheck Service
        |       |
        |       |--> ALLOW
        |       |--> DENY
        |       |--> MANUAL_REVIEW
        |
        |--> Notification Service
        |       |
        |       |--> Send success notification
        |       |--> Send decline/refund notification
        |
        |--> Security System
                |
                |--> Send fraud alert
```
