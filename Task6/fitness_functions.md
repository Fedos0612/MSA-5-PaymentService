# Task 6. Fitness-functions для платёжной системы OrchestrPay

| Название функции | Назначение | Что проверяется | Действие при нарушении | Способ реализации |
|---|---|---|---|---|
| `SagaStateConsistency` | Проверять консистентность состояний Saga | У каждой Saga есть корректное текущее состояние, состояние соответствует последнему выполненному BPMN-шагу, нет невозможных переходов вроде `SUCCEEDED` после `DENY` | Перевести Saga в статус `INCIDENT`, отправить алерт DevOps/SRE, запретить дальнейшее выполнение до разбора | Scheduled job, который сверяет таблицу `saga_states`, историю Zeebe и статусы платежей в `Payment Service` |
| `PaymentStatusConsistency` | Проверять согласованность статусов платежа между сервисами | Статус платежа в `Payment Service` совпадает с состоянием процесса в Camunda: например, если Saga завершена как `REFUNDED`, платёж не должен быть в статусе `DEBITED` | Запустить reconciliation-процедуру, создать инцидент в Operate, отправить алерт в мониторинг | Cron job или отдельный reconciliation worker, который сравнивает данные `Payment Service`, Zeebe и event log |
| `NoMoneyStuckAfterDebit` | Выявлять ситуации, где деньги списаны, но процесс не завершён | Платёж находится в статусе `DEBITED`, `PROCESSING`, `FRAUD_CHECK_IN_PROGRESS` или `TRANSFER_IN_PROGRESS` дольше допустимого времени | Автоматически запустить компенсацию `REFUND_CUSTOMER_ACCOUNT`, уведомить клиента и создать инцидент | Scheduled job, который ищет платежи после списания без финального статуса дольше заданного SLA |
| `SagaFinalStateCompleteness` | Обеспечивать завершённость Saga-транзакций | Каждая Saga должна завершиться одним из финальных статусов: `SUCCEEDED`, `REFUNDED`, `FAILED`, `BLOCKED_AND_REFUNDED` | Создать инцидент, отправить алерт, при наличии списания инициировать возврат | Scheduled job по таблице Saga и данным Zeebe Operate |
| `FraudDenyCompensationRequired` | Контролировать обязательный возврат при отказе антифрода | Если `fraudDecision = DENY`, то должны быть выполнены `MARK_PAYMENT_BLOCKED`, `REFUND_CUSTOMER_ACCOUNT`, `SEND_DECLINE_NOTIFICATION`, `SEND_SECURITY_ALERT` | Автоматически доинициировать недостающий шаг или перевести процесс в incident для ручного разбора | BPMN error boundary events + scheduled consistency checker по истории шагов Saga |
| `ManualDenyCompensationRequired` | Контролировать обязательный возврат при отказе ручной проверки | Если `manualDecision = DENY`, то платёж должен быть заблокирован, клиенту должен быть выполнен возврат, безопасность должна получить уведомление | Запустить компенсационный процесс, создать алерт безопасности, если уведомление не отправлено | Reconciliation worker, который проверяет переменные процесса и выполненные job-ы |
| `RefundCompletionControl` | Контролировать успешность автоматических возвратов | Каждый запущенный возврат должен завершиться статусом `REFUNDED`; не должно быть возвратов в статусе `REFUND_IN_PROGRESS` дольше лимита | Повторить возврат, при исчерпании retry создать критический инцидент и алерт в поддержку/финансы | Scheduled job + retry policy в Zeebe worker `refund-customer` |
| `TransferAfterApprovalOnly` | Обеспечивать целостность Saga после pivot-точки | `TRANSFER_TO_COUNTERPARTY` может выполняться только после `ALLOW`, `APPROVED_BY_CUTOFF` или `manualDecision = ALLOW` | Остановить процесс, создать incident, запретить перевод контрагенту | ArchUnit-тесты для кода + BPMN model validation + runtime checker переменных процесса |
| `NoRefundAfterSuccessfulTransfer` | Предотвращать некорректную компенсацию после успешного перевода | После успешного `TRANSFER_TO_COUNTERPARTY` не должен запускаться `REFUND_CUSTOMER_ACCOUNT` в рамках той же Saga без отдельного dispute/refund-процесса | Остановить компенсационный шаг, создать инцидент для финансового разбора | Runtime checker по event log и BPMN history |
| `ManualReviewDeadlineControl` | Контролировать дедлайн ручной проверки | User task `Manual antifraud review` не должна висеть дольше 20 минут без решения | Сработать по cut-off-time, автоматически считать транзакцию разрешённой и продолжить процесс | Boundary timer event в BPMN: `PT20M` + мониторинг открытых user tasks |
| `CutoffTimerControl` | Проверять корректность срабатывания cut-off-time | Если антифрод или ручная проверка не дали финальный ответ в срок, процесс должен перейти в `APPROVED_BY_CUTOFF` и продолжить перевод | Принудительно применить `APPLY_CUTOFF_ALLOW`, создать предупреждающий алерт | BPMN boundary timer + scheduled audit job по задачам без ответа |
| `FraudCheckTimeoutControl` | Контролировать таймаут ответа антифрод-сервиса | `RUN_FRAUD_CHECK` не должен выполняться дольше допустимого технического таймаута | Повторить запрос по retry policy, затем применить fallback/cut-off или создать incident | Zeebe job timeout, retry policy, метрики длительности job-а |
| `ProcessStuckDetector` | Выявлять зависшие процессы | Процесс находится в промежуточном состоянии дольше допустимого времени: `DEBITED`, `WAITING_MANUAL_REVIEW`, `TRANSFER_IN_PROGRESS`, `REFUND_IN_PROGRESS` | Создать incident, отправить алерт, при списанных деньгах инициировать возврат | Scheduled job, который проверяет длительность активных process instances в Zeebe/Operate |
| `ZeebeIncidentMonitor` | Быстро выявлять технические ошибки процесса | В Operate появились incidents по процессу `orchestrpay-payment-process` | Отправить алерт DevOps/SRE, остановить автопроведение новых платежей при массовой ошибке | Prometheus/Grafana alerting по Zeebe/Operate metrics или polling Operate API |
| `IdempotencyKeyControl` | Предотвращать двойное списание, перевод или возврат | Для каждого `paymentId` и `sagaId` операции `DEBIT`, `TRANSFER`, `REFUND` выполняются не более одного раза в успешном статусе | Заблокировать повторную операцию, вернуть ранее сохранённый результат, создать warning в логах | Уникальные ключи в БД, idempotency table, проверка в workers перед выполнением операции |
| `DuplicateTransferDetector` | Выявлять двойной перевод контрагенту | Для одного `paymentId` не должно быть двух успешных операций `TRANSFER_TO_COUNTERPARTY` | Создать критический финансовый инцидент, заблокировать повторный перевод, запустить reconciliation с финансами | SQL constraint + scheduled reconciliation по ledger/payment_operations |
| `DoubleRefundDetector` | Выявлять двойной возврат клиенту | Для одного `paymentId` не должно быть двух успешных возвратов без отдельного основания | Заблокировать повторный возврат, создать финансовый инцидент | Уникальный индекс по `paymentId + refundType`, проверка перед worker-ом `refund-customer` |
| `NotificationConsistency` | Проверять, что клиент получил корректное уведомление | При `SUCCEEDED` должно быть отправлено success-уведомление; при `REFUNDED`, `FAILED`, `BLOCKED` — decline/refund-уведомление | Повторить отправку уведомления, если retry исчерпан — создать задачу для поддержки | Scheduled job, который сверяет финальные статусы платежей и статусы уведомлений |
| `SecurityAlertConsistency` | Контролировать уведомления безопасности | При `fraudDecision = DENY` или `manualDecision = DENY` должно быть отправлено `SEND_SECURITY_ALERT` | Повторить отправку alert-а, при ошибке создать security incident | Event-driven checker или scheduled job по suspicious transactions |
| `BpmnModelValidation` | Проверять корректность BPMN-модели до деплоя | В BPMN есть start/end events, все service tasks имеют `zeebe:taskDefinition`, gateway имеют условия, user task имеет boundary timer | Запретить деплой некорректного процесса | CI/CD job с BPMN XML validation и автотестами структуры модели |
| `WorkerAvailabilityCheck` | Проверять, что для каждого BPMN service task есть worker | Для каждого task type из BPMN существует Java worker: `create-payment`, `debit-customer`, `fraud-check`, `refund-customer` и т.д. | Остановить деплой, если worker отсутствует | Интеграционный тест в CI, который парсит `process.bpmn` и сверяет task types с зарегистрированными workers |
| `BusinessSlaPaymentControl` | Контролировать SLA успешных транзакций | Успешные платежи должны завершаться менее чем за 5 секунд в 90% случаев | Отправить алерт, если SLA нарушен, создать задачу на анализ узкого места | Prometheus/Grafana metrics по длительности процесса от `CREATE_PAYMENT` до `SUCCEEDED` |
| `RefundSlaControl` | Контролировать скорость автоматических возвратов | Возврат после отказа антифрода или сбоя перевода должен выполняться в заданный срок | Повторить возврат, создать критический алерт, если деньги не возвращены | Метрики по длительности от `REFUND_CUSTOMER_ACCOUNT started` до `REFUNDED` |
| `EventLogCompleteness` | Проверять полноту аудита Saga | Для каждого платежа должны быть записаны события ключевых шагов: создание, списание, проверка, перевод/возврат, уведомление | Создать audit incident, повторно записать недостающие события из истории Zeebe, если возможно | Outbox pattern + scheduled audit checker |
| `DataReconciliationWithLedger` | Проверять финансовую консистентность с внутренним ledger | Сумма списания, перевода и возврата должна соответствовать сумме платежа; баланс операций должен сходиться | Создать финансовый инцидент, заблокировать выплату/закрытие дня до сверки | Scheduled reconciliation job между `payments`, `payment_operations`, ledger и событиями Saga |
| `RetryExhaustionMonitor` | Отслеживать исчерпание retry по критичным job-ам | У job-ов `debit-customer`, `transfer-to-counterparty`, `refund-customer`, `notify-decline`, `send-security-alert` не должны исчерпываться retry без incident | Создать incident, отправить алерт в DevOps/SRE и владельцу домена | Zeebe incident monitoring + alerting по количеству failed jobs |
| `SafeFallbackPolicyCheck` | Проверять, что fallback не нарушает бизнес-правила | Cut-off может разрешить транзакцию только после истечения заданного времени, а не раньше | Остановить процесс, создать incident, если cut-off применён преждевременно | Runtime validation переменных времени + тесты BPMN timer boundary event |
| `ProcessVersionCompatibility` | Проверять совместимость версий BPMN и Java workers | Версия задеплоенного BPMN-процесса совместима с версией `payment-service`, все task type поддерживаются сервисом | Запретить деплой несовместимой версии или откатить релиз | CI/CD check: contract test между `process.bpmn` и кодом workers |
